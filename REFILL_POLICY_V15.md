# Refill policy trial, 19 November 2026

## Rules and compatibility

This release is active after its migration and backend deploy; no feature flag is required. It preserves the existing v14 refill/holdout allocation. Players permitted to refill receive a separate persistent `refill-v15-20261119` assignment: `control_300` (300 seconds) or `treatment_120` (120 seconds), selected by a versioned hash and stored once. Existing owner/QA exclusions or configured analytics-test/recovery identities receive `qa_120` and are excluded from the report. Later QA exclusion never reassigns an existing cohort.

Both trial arms offer at 30% and may prepare at 40% of the current cap. Ad display remains an explicit player action. Preparing, a failed advert, a client event, or an unconfirmed attempt never grants energy or begins the successful-claim cooldown. A valued provider receipt plus the existing atomic claim fills energy to the current cap exactly once. Free regeneration, VIP pricing/perks, rank thresholds, and daily rewards are unchanged.

The server rejects new preparation above 40%, keeps the 60-second unconfirmed-attempt retry gate and 48-hour attempt lifetime, and allows an earned refill below full energy even after regeneration crosses the offer threshold. The frontend's ready cache remains 30 seconds. Already prepared or claimable rewards may remain reachable until full.

## API contract

The `sp_emergency_energy` mission and a successful start carry:

```json
{
  "refill_policy": {
    "version": "refill-v15-20261119",
    "group": "treatment_120",
    "cooldown_seconds": 120,
    "offer_threshold_pct": 30,
    "prepare_threshold_pct": 40,
    "ready_ttl_ms": 30000,
    "retry_seconds": 60
  }
}
```

The mission also carries `prepare_available`, true only for an enabled, permitted, available refill with authoritative projected energy at or below 40% and below full. `status: available` remains independent of energy. Existing cooldown/countdown, pending, claimable, attempt ownership, and zone fields remain authoritative. A paused or nonenrolled holdout mission may have a null policy and cannot prepare. Old clients still prepare at their stricter threshold and use the same verified reward endpoints.

`POST /api/mission/outcome` accepts `offer/PROMPT_SHOWN` with `attempt_id: null`, and `preload/PREPARED` or `preload/PREPARED_EXPIRED` with an owned versioned refill attempt. Optional `elapsed_ms` is an integer from 0 through 300000. The server derives policy, cohort, and identity; caller-supplied policy/identity/value fields are discarded. Observations use a separate 40-per-player-per-ten-minute process limit; failures keep the existing 12-report limit. PostgreSQL deduplicates each ready/expiry event per attempt and each prompt per player/version/minute across processes. These observations never prove a billable impression or modify a reward.

## Roll forward

1. Review and apply `sql/migrations/20261119152941_refill_policy_trial.sql` before deploying backend code. It was generated by pinned Supabase CLI 2.81.3 in a disposable local directory and moved, with its generated name, into the repository's existing migration directory.
2. Verify the private tables have RLS enabled and no PUBLIC/anon/authenticated privileges; verify the ad-attempt check allows 120 seconds only for energy refills. The migration preserves 86400, legacy 3600 energy/double, 300 coins/energy, and 1800 double values. No existing attempts or v14 group rows are rewritten.
3. Deploy backend, then frontend. Check signed mission responses for both trial arms and QA. Startup explicitly checks the three private v15 tables and fails with `INSTALL_REFILL_V15_MIGRATION` if the migration is missing, instead of accepting traffic and guessing a cohort.
4. A treatment player's preexisting cooldown can shorten to 120 seconds from the original claim; a control player's remains 300. Existing confirmed 300/3600/86400 attempts still claim once, applying the shorter of their recorded wait and that player's current policy.

## Roll back

Roll back the frontend and backend code while retaining this additive migration and all stored assignments, observations, and receipts. Do not drop tables or narrow the cooldown check: 120-second receipts may already exist. The preceding backend understands stored attempts and honors an already saved shorter cooldown, while creating subsequent 300-second attempts. Reapplying this release resumes the same cohorts. Record the rollback interval when interpreting results; it is not exposure to the intended experiment.

## Read-only scorecard and limits

Run `sql/refill_scorecard_v15.sql` as the private database owner. It groups by version, UTC assignment day, and cohort, excludes QA/system/acquisition-excluded users and existing holdouts, and reports the first 30 days' attempts, confirmed receipts, claims, prompt observations, ready/expired preparations, gross confirmed purchases/VIP purchases, paid Stars, separately refunded Stars, and D7 return. Purchase counts include purchases later refunded; they are not net sales. D7 is a return recorded through a later refill-policy lookup in hours 168–192; the denominator matures at hour 192.

Provider estimated impression USD is explicitly labelled and never treated as settled revenue. Actual cohort net GBP and contribution stay NULL until a complete 30-day window and separately evidenced, fully allocated totals exist in `refill_finance_v15`. Never split old v14 totals by player counts or manufacture an exchange rate. Report both arms' sample sizes and uncertainty before declaring a winner; this trial does not establish an optimal cooldown or guarantee advert availability or revenue.
